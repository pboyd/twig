# Implementation Plan: User Authentication

**Branch**: `003-user-auth` | **Date**: 2026-05-19 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/003-user-auth/spec.md`

## Summary

Add authentication and per-user task isolation to the existing `services/todo`
backend. Two credential types resolve to one user: a session cookie issued by a
username/password login (browser clients) and a long-lived API key sent as a
`Bearer` token (CLI clients). A single `net/http` middleware sits in front of
the Connect-Go task handlers, checks the `Authorization` header then the session
cookie, and injects the resolved `user_id` into the request context. Two plain
HTTP endpoints — `POST /auth/login` and `POST /auth/logout` — manage session
lifecycle and bypass the middleware. The `tasks` table gains a `user_id` column,
every task query gains a `WHERE user_id = $n` filter, and the task handlers read
`user_id` from the request context, leaving the `TaskService` wire contract
(`task.proto`) unchanged. User accounts and API keys are created at deploy time
via a `--provision-user` server flag. The CLI sends its API key on every
request via a request-header interceptor.

## Technical Context

**Language/Version**: Go 1.25 (existing `services/todo` module — no new module)

**Primary Dependencies**: Existing — Connect-Go (`connectrpc.com/connect`
v1.19.2), `pgx/v5`, `golang-migrate/v4`, generated `taskv1`/`taskv1connect`.
New — `golang.org/x/crypto/bcrypt` for password hashing. `crypto/rand`,
`crypto/sha256`, `crypto/subtle`, `encoding/hex`, `encoding/json`, and
`net/http` cookie support come from the standard library.

**Storage**: PostgreSQL via `pgx/v5`; schema managed by `golang-migrate`
file migrations; query code generated by `sqlc` v1.31.1. New migration
`000003_auth` adds `users`, `sessions`, `api_keys` and the `tasks.user_id`
column. New query file `db/queries/auth.sql`; `db/queries/task.sql` modified.

**Testing**: `go test` — table-driven unit tests for credential helpers
(bcrypt round-trip, token generation, SHA-256 key hashing, constant-time
compare); middleware tests with `httptest`; auth-endpoint tests against an
in-memory or test database; task-handler tests extended to assert per-user
isolation. Existing handler tests are updated to supply a `user_id` context.

**Target Platform**: Single Linux server binary (`cmd/server`) behind HTTPS on
a trusted LAN; the existing `todo` CLI binary (`cmd/todo`) is the API-key client.

**Project Type**: Web service (Connect-Go backend) plus its companion CLI —
both already exist in one Go module; this feature extends both.

**Performance Goals**: Per-request auth overhead negligible relative to the
existing task RPCs (one indexed credential lookup per request). bcrypt cost
factor 12 keeps a login verification well under one second on server hardware.

**Constraints**: Session cookies set `HttpOnly; Secure; SameSite=Strict`;
service assumed to run over HTTPS. No brute-force protection on login (spec
clarification — out of scope). `task.proto` and the generated Connect code
remain unchanged — user scoping is server-side and invisible to clients.

**Scale/Scope**: One or two users per instance; one API key per user at
provisioning time; default session lifetime 30 days (configurable).

**Structure Decision**: The feature extends the existing single `services/todo`
module in place. All new server-side auth logic lives in one new package,
`internal/auth`, mirroring the existing flat `internal/handler` and
`internal/cli` layout. No new module, no new top-level directory. Database
access stays generated by `sqlc`; the auth middleware is ordinary `net/http`
handler composition so it can read the `Authorization` header and `Cookie`
before the request reaches the Connect mux. The CLI change is confined to client
construction in `cli.go`.
