# Phase 0 Research: Ansible Deployment

Resolves open technical choices for the plan. Each decision is recorded with rationale and the alternatives considered.

## 1. Reverse proxy

**Decision**: Caddy v2 (`docker.io/library/caddy:2-alpine`), config via a templated `Caddyfile`.

**Rationale**: Single-file config; first-class support for adding TLS later by changing one line (the site label) — directly satisfies FR-015's "structured so TLS can be added later without re-architecting." Smaller cognitive surface than nginx. Already widely packaged as a container.

**Alternatives considered**:

- **nginx**: More configuration ceremony (multiple files, separate stream/http blocks). TLS retrofitting requires additional files for certs and renewal hooks.
- **Traefik**: Excellent dynamic config story but oriented around container-label discovery; overkill for a fixed two-service backend (server only) on one host.
- **No proxy / direct port bind**: Rejected via clarification Q1.

## 2. On-host image registry

**Decision**: Upstream `docker.io/library/registry:2`, bound to `127.0.0.1:5000` on the VM (not exposed to the LAN), backed by a host bind-mount at `/var/lib/todo/registry/`.

**Rationale**: De-facto standard registry implementation. Bind-mounting the storage to a host path satisfies FR-007a (persistence across reboots). Localhost-only binding satisfies the assumption that the registry is not exposed to the broader network. The maintainer pushes to it over SSH by port-forwarding 5000 from their workstation.

**Alternatives considered**:

- **Skopeo direct copy** without a registry: would conflict with FR-004 (explicitly requires a registry).
- **Harbor / Zot**: heavier; auth/UI features not needed for a single-user setup.
- **Expose the registry on the LAN**: rejected because the spec assumption is registry stays private to the VM.

## 3. How the maintainer pushes images to the on-host registry

**Decision**: Open an SSH local port-forward (`ssh -L 5000:127.0.0.1:5000 user@vm`) for the duration of the build/push step, then push to `localhost:5000/todo-server:<tag>` from the workstation. The Ansible playbook runs this via an `ansible.builtin.shell` block on the local host using `delegate_to: localhost`.

**Rationale**: Reuses the SSH key the playbook is already authenticated with. No new ports exposed on the VM. Works identically against any target VM regardless of network topology.

**Alternatives considered**:

- **Expose the registry on the VM's LAN interface and push directly**: violates the "registry private to VM" assumption; would also require Ansible to manage `/etc/containers/registries.conf` for insecure registries on the workstation.
- **`podman save` → scp → `podman load`**: works but bypasses the registry entirely; FR-013 requires the production compose to reference images by registry coordinates.

## 4. Image tag strategy

**Decision**: Two tags pushed per deploy — a content tag derived from `git rev-parse --short HEAD` (e.g. `todo-server:a3832d3`) and a moving `todo-server:latest`. The rendered compose file pins to the content tag, not `:latest`.

**Rationale**: Pinning to the commit SHA gives idempotent compose runs (FR-009): if the compose file's image reference is unchanged, podman-compose will not recreate the container. `:latest` is kept around purely for ad-hoc inspection (`podman pull localhost:5000/todo-server:latest`).

**Alternatives considered**:

- **`:latest` only**: would force recreate on every run, defeating idempotency.
- **Timestamp tags**: not reproducible; SHA is the natural identifier.

## 5. Auto-start on VM reboot

**Decision**: One systemd unit per compose project, generated by `podman-compose systemd` style boilerplate written by the playbook. Specifically: a small `todo.service` unit that runs `podman-compose up -d` against the production compose file in the app's working directory, with `WantedBy=multi-user.target` and `Restart=on-failure`. A separate `registry.service` is created by the registry role with the same shape against the registry compose file.

**Rationale**: Satisfies FR-008 (stack returns after reboot) and FR-008a (containers restart on crash, via `restart: unless-stopped` in the compose file itself). Two units rather than one because the registry must be up before the app can pull on boot — `todo.service` has `After=registry.service` and `Requires=registry.service`.

**Alternatives considered**:

- **`podman generate systemd` per container**: produces per-container units; harder to keep in sync with the compose file as services are added.
- **Rootless user units (`systemctl --user`)**: would require `loginctl enable-linger`. Rejected for now in favor of root services to match the dev environment's privilege model and keep the boot ordering simple.
- **No systemd, rely on `podman-compose up` from a cron `@reboot`**: fragile, no dependency ordering.

## 6. Host filesystem layout

**Decision**:

```text
/var/lib/todo/
├── postgres/         # PG data dir, owned by uid:gid matching the postgres container's user
├── registry/         # registry blob storage
└── app/
    ├── compose.yaml  # rendered production compose
    └── Caddyfile     # rendered proxy config
```

**Rationale**: One root directory makes backup and inspection trivial (out of scope for this feature, but won't be obstructed). Separating `app/` (config) from `postgres/` and `registry/` (data) means a future "wipe the app, keep the data" operation is a single `rm` away.

## 7. Port exposure on the VM

**Decision**: Only Caddy is exposed on the VM's host interface (`:80`, bound to `0.0.0.0`). The application server and PostgreSQL bind only to the compose network. The registry binds to `127.0.0.1:5000` on the host.

**Rationale**: Minimizes attack surface, matches FR-015 (proxy is the only network entry point). PostgreSQL stays private to the compose network.

## 8. Observability (deferred from clarify)

**Decision**: Rely on `podman logs` and `journalctl -u todo.service` for this feature. No log aggregation, no metrics, no tracing.

**Rationale**: Single-user personal deployment; the cost of adding a logging pipeline isn't justified yet. The systemd units already capture stdout/stderr into the journal, which is searchable from the VM.

**Future work** (out of scope here): if/when a second VM or external monitoring is introduced, revisit.

## 9. Old image cleanup (deferred from clarify)

**Decision**: No automatic cleanup in this feature. The registry will accumulate one tagged image per deploy.

**Rationale**: At one deploy per day for one application image, this fills disk on the order of a year before becoming a concern. A future task can add `podman exec registry garbage-collect` if needed; tracked as out-of-scope for now.

## 10. Ansible target Python and module availability

**Decision**: The playbook requires `python3` on the VM (default on Fedora Server). Uses the `containers.podman` collection (`podman_image`, `podman_login`, `podman_container`) where it simplifies tasks, and `community.docker.docker_compose_v2` is **not** used (it speaks the Docker socket, not podman). Compose lifecycle is invoked via `command: podman-compose ...` modules, which is acceptable because the commands are idempotent at the compose level.

**Rationale**: Sticking to standard collections + raw `command` calls for compose keeps the dependency surface minimal and avoids the docker-shim trap.
