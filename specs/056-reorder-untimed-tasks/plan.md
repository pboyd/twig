# Implementation Plan: Reorder Untimed Plan Entries in the TUI

**Branch**: `056-reorder-untimed-tasks` | **Date**: 2026-06-15 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/056-reorder-untimed-tasks/spec.md`

## Summary

Give untimed plan entries (entries on a day with a duration but no start time) a user-defined order, controlled in the TUI Planning tab with the existing `{` / `}` rank-higher / rank-lower keys. Today untimed entries fall out in creation order (`id ASC`) with no way to influence it. The approach mirrors the established task-ordering feature (037): add a persisted `position` column to `plan_entries`, expose a single `ReorderPlanEntry` RPC on the existing `PlanService` that repositions an untimed entry relative to a sibling anchor inside a transaction, and wire `{`/`}` in the TUI's `handlePlanningKey` to call it when the highlight is on an untimed entry. Because the order is stored server-side and folded into the existing day-listing query, the CLI and web app reflect the order for free without gaining any new controls.

## Technical Context

**Language/Version**: Go 1.23 (CLI/TUI + server); the change is server + TUI only (no web/TS work).

**Primary Dependencies**: ConnectRPC (gRPC-compatible) for the new RPC; pgx/v5 + sqlc for the query layer; golang-migrate for the schema change; `charm.land/bubbletea/v2` + `bubbles/v2` for the TUI.

**Storage**: PostgreSQL. `plan_entries` table, PK `(user_id, day, id)`. Add `position SMALLINT NOT NULL DEFAULT 0`.

**Testing**: `go test ./...` (root module, TUI) and `cd services/twig && go test ./...` (handler/db). Handler tests use `export_test.go` shims and do not require a running database.

**Target Platform**: Linux server + terminal TUI client.

**Project Type**: Multi-module Go monorepo (root CLI/TUI, `api/` shared proto, `services/twig/` server). Mirrors the data-flow `TUI → ConnectRPC → handler → db → PostgreSQL`.

**Performance Goals**: Reorder must feel instant in the TUI (single render cycle, per SC-002). Entry counts per day are small (tens at most), so the transactional renumber is trivially fast.

**Constraints**: Order persists across restarts (FR-006); reordering must never lose, duplicate, or re-time an entry (SC-003); confined to the untimed group (FR-004).

**Scale/Scope**: One new DB column + index touch, ~3 new sqlc queries, one new RPC on the existing `PlanService`, one new TUI command factory + two key cases. No new TUI surface, no new CLI/web controls.
