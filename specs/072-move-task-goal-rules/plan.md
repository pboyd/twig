# Implementation Plan: Goal Handling When Moving Tasks

**Branch**: `072-move-task-goal-rules` | **Date**: 2026-08-01 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/072-move-task-goal-rules/spec.md`

## Summary

Moving a task currently either fails with a nested-goal error, leaves a nested task holding its own
goal link, or silently drops the goal a promoted sub-task was displaying. All three are fixed in one
place: the `parent_id` branch of `Task.UpdateTask` in `services/twig/internal/handler/task.go`.

The replacement rule is small: **on a real parent change, a task that lands under a parent gives up
its own goal link (and its descendants' links are cleared too); a task that lands at the root level
is given the goal it was inheriting.** The blocking precondition check is deleted outright.

Three things make this more than a branch rewrite:

1. `UpdateTask` is **full-replace on `parent_id`** — every caller sends the field on every edit, so
   "parent was supplied" cannot mean "parent changed". The goal rules must key off a comparison
   against the stored row, or an ordinary rename would clear a goal link.
2. The write must be **atomic** (FR-011). The handler currently issues five-plus sequential
   `Queries` calls with no transaction. `ReorderTask` in the same file already has the
   `Pool.Begin` / `Queries.WithTx` pattern to copy.
3. Promotion to root today **also skips repositioning**, because that block is guarded by the same
   `req.Msg.ParentId != nil` condition. Fixing the guard fixes a latent position bug alongside the
   goal bug.

No proto change, no client change, no migration.

## Design Outline

### The parent-change decision

Read the stored task inside the transaction, then compare:

| Stored `parent_id` | Requested `parent_id` | Action |
|---|---|---|
| same as requested | — | No parent change. Do not touch `goal_id`. (FR-008) |
| any | non-NULL, different | **Descent**: clear moved task's `goal_id`, clear all descendants' `goal_id`. (FR-002, FR-003) |
| non-NULL | NULL | **Promotion**: if moved task has no `goal_id`, set it to the nearest goal-bearing ancestor's goal, if any. (FR-004, FR-005, FR-006) |

Descent still runs its existing validations — cycle, destination exists, destination not completed —
and those still reject the move (FR-009). Only the goal precondition is deleted (FR-012).

### New queries

- **`NearestAncestorGoal`** — walks `parent_id` upward from the moved task and returns the first
  non-NULL `goal_id`. A depth-ordered variant of the existing `AncestorHasGoal` CTE, returning the
  id rather than a boolean. Must be evaluated **before** the parent is rewritten.
- **`ClearSubtreeGoals`** — recursive `UPDATE ... SET goal_id = NULL` over the moved task's
  descendants. Mirrors the `DescendantHasGoal` CTE.

`AncestorHasGoal` and `DescendantHasGoal` stay — `SetTaskGoal` at `task.go:612` and `task.go:621`
still uses them, and FR-010 keeps that validation exactly as it is.

### Closed goals

FR-007 requires promotion to link a task to a completed or archived goal when that is what it was
inheriting. `SetTaskGoal` refuses such links (`task.go:604`), so promotion writes `goal_id` directly
via the update rather than routing through that handler. This is deliberate and is the one place
where the two paths diverge — see `research.md` decision 5 for the reasoning.

## Out of Scope — flagged, not fixed

`moveTaskCmd` in `internal/tui/update.go:539` builds its `UpdateTaskRequest` without
`SnoozeUntil`. Because `UpdateTask` is full-replace, **moving a task in the TUI silently
un-snoozes it.** This is the same class of bug as commit `1f84006` ("fix(web): preserve snoozeUntil
in task update payload"), which fixed it on the web side only. It sits directly in the move path
this feature touches, but it is a snooze bug, not a goal bug, and the spec does not cover it.
Worth a follow-up feature; say the word and it can be folded in here instead.
